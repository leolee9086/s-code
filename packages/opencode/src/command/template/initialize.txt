为此仓库创建或更新 `AGENTS.md`。

目标是创建一个简洁的指令文件，帮助未来的 OpenCode 会话避免错误并快速上手。每一行都应回答："如果没有帮助，agent 可能会错过这一点吗？"如果不是，就省略。

用户提供的关注点或约束（遵守这些）：
$ARGUMENTS

## 如何调查

首先阅读最高价值的来源：
- `README*`、根清单文件、工作区配置、锁文件
- 构建、测试、lint、格式化、类型检查和代码生成配置
- CI 工作流和 pre-commit / 任务运行器配置
- 现有的指令文件（`AGENTS.md`、`CLAUDE.md`、`.cursor/rules/`、`.cursorrules`、`.github/copilot-instructions.md`）
- 仓库本地的 OpenCode 配置，如 `opencode.json`

如果阅读配置和文档后架构仍不清楚，检查少数代表性代码文件以找到真正的入口点、包边界和执行流程。优先阅读解释系统如何连接在一起的文件，而非随机的叶子文件。

优先选择可执行的真相来源而非叙述性文档。如果文档与配置或脚本冲突，相信可执行的来源，只保留你能验证的内容。

## 提取什么

为在此仓库中工作的 agent 寻找最高信号的事实：
- 确切的开发者命令，尤其是非显而易见的
- 如何运行单个测试、单个包或集中的验证步骤
- 在重要时的必需命令顺序，如 `lint -> typecheck -> test`
- 单体仓库或多包边界、主要目录的所有权以及真正的应用/库入口点
- 框架或工具链的特殊之处：生成的代码、迁移、代码生成、构建产物、特殊环境加载、开发服务器、基础设施部署流程
- 与默认值不同的仓库特定风格或工作流约定
- 测试的特殊之处：fixtures、集成测试先决条件、快照工作流、必需的服务、不稳定或昂贵的测试套件
- 来自现有指令文件的值得保留的重要约束

好的 `AGENTS.md` 内容通常是来之不易的上下文，需要阅读多个文件才能推断出来。

## 问题

仅当仓库无法回答某些重要内容时才向用户提问。最多使用 `question` 工具进行一次简短批处理。

好的问题：
- 未文档化的团队约定
- 分支/PR/发布期望
- 已知但未记录的缺失设置或测试先决条件

不要询问仓库已经说清楚的内容。

## 编写规则

只包含高信号、仓库特定的指导，例如：
- agent 否则会猜错的确切命令和快捷方式
- 从文件名不明显的架构说明
- 与语言或框架默认值不同的约定
- 设置要求、环境特殊之处和操作上的陷阱
- 对重要的现有指令来源的引用

排除：
- 通用软件建议
- 长篇教程或详尽的文件树
- 显而易见的语言约定
- 推测性声明或任何你无法验证的内容
- 更适合存储在通过 `opencode.json` `instructions` 引用的另一个文件中的内容

有疑问时，省略。

优先使用简短的章节和项目符号。如果仓库简单，保持文件简单。如果仓库庞大，总结少数真正改变 agent 工作方式的结构性事实。

如果 `${path}` 处已存在 `AGENTS.md`，就地改进它，而不是盲目重写。保留已验证的有用指导，删除冗余或过时的声明，并将其与当前代码库协调一致。
