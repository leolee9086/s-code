# 打断 vs 入队：外部消息的两种优先级用途

## Ring 0 — 高优先级打断

**目的**：外部系统需要 LLM 立即关注的消息。不等当前轮次结束。

**使用场景**：
- **用户通过聊天工具发新消息**（Discord/Telegram/Slack）：用户期待即时回复，打断正在进行的任务切换到当前对话
- **紧急指令**（停止当前任务/切换上下文）：例如用户告诉 agent "停下手头的事，先做这个"
- **实时通知**（警报/监控/webhook）：系统事件需要 agent 立即处理

**行为**：
1. 中断当前 LLM stream（`processor.ts:810 onInterrupt`）
2. 创建一条带外部消息的 user message
3. 立即重启 loop（`promptSvc.loop`）
4. 模型看到新消息，原子地决定如何处理（继续原任务 / 切换 / 挂起）

## Ring 1-3 — 普通优先级入队

**目的**：非紧急信息，当前轮次结束后自然处理。

**使用场景**：
- **后台查询结果**（web search / file read 等工具异步返回）
- **低优先级通知**（代码编译完成 / 定时任务触发 / 条件引擎信号）
- **批量消息推送**（日志流 / 事件流），不需要每个都打断

**行为**：
1. 注入 `setSuffixOnce`，当前 LLM 轮次正常完成
2. loop 的 `consumeSuffix()` 在下一轮加载消息
3. 模型在下一轮看到注入的消息，决定是否响应该消息

## 为什么必须区分

| 场景 | Ring 0 打断 | Ring 1-3 入队 |
|------|------------|---------------|
| 用户聊天消息 | ✅ 打断，立即响应 | ❌ 用户要等几十秒 |
| 工具异步结果 | ❌ 打断让模型困惑 | ✅ 自然地融入上下文 |
| 紧急指令 | ✅ 必须立即停下 | ❌ 可能错过时机 |
| 日志/事件流 | ❌ 每一条都打断太频繁 | ✅ 批量吸收 |
| webhook 告警 | ✅ 取决于告警级别 | ✅ 取决于告警级别 |

两种模式共存的理由：**不是所有外部消息都紧急，但紧急消息不能被轮次边界延迟**。
